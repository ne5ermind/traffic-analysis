# Реестр требований InnovaTransport

Реестр связывает каждое требование со способом проверки. Источник и текущий статус намеренно не включены: для приёмки обязательны момент проверки, метод и однозначный ожидаемый результат.

Подробное описание требований находится в [`FR.md`](./FR.md) и [`NFR.md`](./NFR.md).

## Функциональные требования

| ID | Требование | Когда проверять | Как проверять | Критерий приёмки |
|---|---|---|---|---|
| F-01 | Пользователь загружает видеозапись для анализа | После изменения загрузки и перед каждым релизом | Загрузить поддерживаемый и некорректный файлы через UI и API | Корректное видео появляется в каталоге; неподдерживаемый файл отклоняется с понятной ошибкой |
| F-02 | Пользователь запускает анализ и видит его состояние | После изменения очереди, worker или экрана анализа | Создать запуск, проследить смену состояний и проверить отмену | Запуск проходит состояния «в очереди» → «в работе» → «завершён» либо завершается явной ошибкой/отменой |
| F-03 | Система обнаруживает транспорт и пешеходов | После изменения модели, обработки кадров или порогов | Запустить анализ размеченного тестового фрагмента и проверить сохранённые detections | Для целевых объектов сохраняются bbox, confidence, class ID и tracker ID; некорректные рамки отбрасываются |
| F-04 | Система классифицирует объекты по поддерживаемым категориям | После изменения набора классов или агрегации | Проверить результаты на фикстурах всех поддерживаемых категорий | Объекты относятся только к категориям pedestrian, bicycle, car, motorcycle, bus и truck; итоги разделены по категориям |
| F-05 | Система считает транспортные и пешеходные потоки без повторного учёта | После изменения трекинга или логики подсчёта | Прогнать синтетические траектории и контрольный видеофрагмент | В автоматическом режиме устойчивый tracker ID учитывается один раз; в режиме зоны учитываются подтверждённые пересечения |
| F-06 | Пользователь задаёт и изменяет зону подсчёта | После изменения редактора сцены или геометрии | Создать ROI и линии, сохранить сцену, повторно открыть и перезапустить анализ | Координаты сохраняются без искажения, видны поверх видео и используются новым запуском анализа |
| F-07 | Пользователь получает сводные результаты анализа | После изменения API результатов или расчёта итогов | Сравнить события с KPI и таблицей направлений | Общий итог равен сумме учтённых событий; отдельно показаны транспорт, пешеходы и категории |
| F-08 | Система строит таблицы, диаграммы и картограмму | После изменения визуализации или маршрутизации | Открыть результаты готового запуска и затем изменить событие | Визуализации строятся из текущих данных и обновляются после ревизии события |
| F-09 | Пользователь просматривает видео с синхронным overlay | После изменения проигрывателя или detections API | Выполнить воспроизведение, seek и смену запуска | Рамки, категории, tracker ID и зоны соответствуют текущему времени; старые рамки очищаются |
| F-10 | Система сохраняет и экспортирует результаты | После изменения хранения или экспорта | Перезапустить сервис и скачать XLSX, CSV и JSON | Результаты остаются доступны; файлы открываются, относятся к нужному запуску и содержат согласованные итоги |

## Нефункциональные требования

| ID | Требование | Когда проверять | Как проверять | Критерий приёмки |
|---|---|---|---|---|
| NF-01 | Быстрый режим обрабатывает 15 минут видео не дольше 30 минут на целевой конфигурации | Перед релизом и после изменения модели, sampling или worker | Полный benchmark 15-минутного видео в Docker с 4 CPU-потоками | Время обработки ≤ 30 минут; параметры машины, видео и частота выборки записаны в отчёте |
| NF-02 | Пользователь не остаётся в бесконечном ожидании при сбое worker | После изменения heartbeat и обработки ошибок | Остановить worker во время анализа и дождаться порога контроля | Не позднее чем через 5 минут интерфейс показывает ошибку и понятную причину вместо вечного статуса обработки |
| NF-03 | Видео и результаты обрабатываются локально | Перед релизом и после добавления интеграций | Проверить сетевые обращения приложения во время загрузки, анализа и экспорта | Пользовательские видео и результаты не отправляются во внешние сервисы |
| NF-04 | Система защищает целостность сохранённых результатов | После изменения схемы БД, событий или ревизий | Выполнить параллельные правки одной версии события и проверить журнал | Устаревшая правка отклоняется с конфликтом; успешная правка имеет новую версию и запись в revisions |
| NF-05 | Основной сценарий понятен русскоязычному пользователю | При изменении интерфейса и перед демонстрацией | Пройти загрузку → анализ → проверку → экспорт без обращения к коду | Основные действия и ошибки подписаны по-русски; сценарий завершается через UI |
| NF-06 | Проект переносим между локальным запуском и Docker | После изменения путей или хранения | Создать данные локально, подключить тот же каталог в Docker и выполнить обратную проверку | Видео, модели и результаты находятся по переносимым путям и остаются доступными в обоих режимах |
| NF-07 | Поддерживаются заявленные среды запуска | Перед релизом и после изменения зависимостей | Запустить smoke test на Python 3.11/3.12 и через Docker Compose | API, worker, Swagger, видео и экспорт запускаются без изменения исходного кода |
| NF-08 | Изменения автоматически проверяются | Для каждого Pull Request | Запустить GitHub Actions | Проходят 46 pytest-тестов, compileall, проверка JavaScript и `docker compose config` |
| NF-09 | Публичный API документирован и остаётся компактным | После изменения маршрутов API | Открыть `/docs` и проверить `/openapi.json` автоматическим тестом | Swagger доступен; в публичной схеме ровно 10 согласованных API-путей |
| NF-10 | Интерфейс пригоден для основных размеров экрана | После изменения HTML/CSS и перед релизом | Проверить desktop, mobile portrait и mobile landscape | Основные элементы доступны, текст читаем, действия не перекрываются, критичный контент не теряется |

## Правило приёмки

Требование считается выполненным только тогда, когда воспроизводимо пройдена указанная проверка и достигнут критерий приёмки. Для требований компьютерного зрения отдельная оценка точности выполняется только на размеченном наборе с frame-level bbox и tracker ID; агрегированные таблицы не заменяют такой эталон.
